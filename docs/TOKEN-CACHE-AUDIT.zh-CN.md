# 子代理用量与缓存审计（2026-11-03）

结论：缓存已经大量命中。当前消耗主要表现为长任务中模型调用次数多、上下文不断增长，以及主代理与子代理使用不同价格的模型。继续优化缓存有价值，但需要与缩小工作范围、减少重复输入和控制循环次数一起做。

## 证据与口径

- 读取两个父会话和 18 个子会话的本地持久日志，逐条汇总 `assistant/message.usage`，没有发起新的模型请求。
- 原始日志与 `session_projcache` 用量投影的四个桶在最终采样时全部一致（20/20）。采样时刻见 [JSON 证据](evidence/2026-11-03-native-token-audit.json)。记录不含提示词、文件内容、凭证或请求头。
- DSH 0.2.1-rc.5 子代理菜单的 `tokenTotal()` 会相加：未缓存输入、缓存读取、缓存写入、输出。因此菜单里的 `34M tok` 包含反复读取的缓存，不能解释为 3400 万新生成或全价输入。
- 本机 pi-ai adapter 的 `inputTokens` 是未缓存输入；其 OpenAI 解析先从 `prompt_tokens` 扣除缓存读取/写入。输出已经包含供应商报告的 reasoning tokens，不能把 reasoning 再加一次。
- 输入缓存命中率 = 缓存读取 ÷（未缓存输入 + 缓存读取 + 缓存写入）。本次缓存写入桶均为 0，不代表服务器没有创建缓存。

## KV / Prompt Cache 应怎样进一步复用

服务端缓存与本地会话恢复是两件事。恢复 child 可保留对话历史；是否命中 KV 还取决于供应商、模型、路由、前缀一致性和服务端保留情况。OMC 不能将 Go 的 KV 导出给 MiMo，也不能用磁盘存一份对话就宣称保存了远端 KV。

1. **每个会话发送稳定、独立的会话标识。** 同一 child 的后续 turn、重试和压缩请求保持同一标识；新 child 使用自己的标识。不要让所有 child 共用一个固定值，也不要每次请求生成新值。OpenCode 官方要求客户端发送 `x-opencode-session`，并将 DSH 列为部分路径缺少会话信息的客户端。[OpenCode Go 官方说明](https://opencode.ai/v2/docs/console/go/#where-can-i-use-it)
2. **固定前缀，将变化放后面。** 保持角色系统提示、工具定义及排序稳定；任务指令与阶段进度放在后续消息，避免每轮重写前面的系统文本。不要在固定前缀中不断加入当前时间、随机 ID 或整份动态状态。
3. **同一个短期工作继续原 child。** 用原生 `send_message` 续接同一项修正；避免把同一份材料发给全新的 child 重新勘探。进入独立工作包时用简短交接创建新上下文，避免一个 child 无限膨胀。跨供应商交接依靠已验证事实和文件路径，不依靠 KV。
4. **不要把 `cacheRetention: long` 当作通用开关。** DeepSeek 官方说明其上下文缓存自动启用、按前缀匹配且尽力命中；Anthropic 的 `cache_control`/TTL 或 OpenAI 的 retention 参数不能直接推广到 Go DeepSeek。[DeepSeek 缓存文档](https://api-docs.deepseek.com/guides/kv_cache/)

### 本机路由检查：尚需补齐的部分

在实际安装的 rc.5 ASAR 中检查到：

- `dsh-llm-pi-ai` 将 `options.sessionId` 传入 pi-ai。
- 其 `requestHeaders(profile.headers)` 只合并静态头和 attribution；attribution 目前仅提供 User-Agent。
- `pi-ai/dist/api/openai-completions.js` 的通用会话亲和头受兼容开关控制，名称不包含 `x-opencode-session`。
- Desktop profile 没有显式配置 `x-opencode-session` 或 `sessionHeader`。

这表明动态会话标识存在需要修复/验证的适配缺口，与官方问题说明一致；**本次没有抓取线上 HTTP，请求头是否在其他路径被补入尚未逐路验证。不能据此声称本次缓存全部失效**，实际日志已经反证了“完全没缓存”。

适配修复应位于实际发送请求的 LLM 层：从当前 `GenerateOptions.sessionId` 注入动态头，覆盖普通聊天、子代理、总结和标题请求。验收必须包括同一 child 多轮值不变、不同 child 值不同、重试/恢复稳定，以及 provider 返回的真实缓存用量。不要用统一静态 header 临时冒充正确实现。

## OMC 下一步开发顺序

下面是建议的工程起点，**尚未修改正在运行的 profile，也没有声称已经实现预算限制**。

| 优先级 | 应实现的行为 | 初始建议与验收 |
|---|---|---|
| P0 用量展示 | 分开显示新输入、缓存、输出、调用次数、实际 provider/model | 复用持久 tokenUsage；缓存率按输入计算；价格未知显示 unknown。保留总 token，避免把总数误作全价消耗。 |
| P0 预算治理 | 父任务和 child 分别记录成本与步数，达到预算先产出检查点，再决定是否继续 | Explorer 先以 12–20 次模型响应为软检查点；Fixer 先以 30–50 次为软检查点。复杂任务允许继续，但要展示原因和新增预算。不要在编辑中途直接强杀。 |
| P0 上下文约束 | 工具输出限额、窄范围读取、长日志落文件、使用交接摘要 | 工具回显先以 8–16K 字符为软限额；超出时返回摘要与文件定位。文件内容和验收证据必须仍可按需读取。 |
| P1 缓存亲和 | 补齐逐会话动态 header，并验证每条实际 adapter 路径 | 固定 provider/model，稳定前缀；用真实返回字段衡量，不能仅凭请求里写了 header 就判通过。 |
| P1 工作包与压缩 | 按交付物拆分实现/验证，达到上下文检查点再总结 | 可先试 Explorer 40–60K、Fixer 80–120K 输入检查点；它们是工作流建议，不是现有 OMC 配置字段。总结后记录冷启动代价与后续收益。 |
| P1 路由成本 | 主代理与子代理一起预算；常规协调使用低成本模型，关键审查再升级 | 比较“单次任务最终成本与质量”，不能只比较每百万 token 单价；降低模型能力可能增加循环。 |

当前 rc.5 已有 `dsh-compaction-basic` 的 `modelPolicies/thresholdRatio/retainTokens` 和工具结果裁剪服务，不需要从零造压缩器。但安装代码的默认压缩触发比例为上下文窗口的 0.8；百万窗口可能很晚才触发。Desktop patch 没有显示这些参数的显式覆盖，宿主其他默认配置仍需在应用变更前核对。工具裁剪在触发压缩路径后执行，不等于每次工具输出都会立刻被裁剪。

压缩和新上下文会改变旧前缀，可能先出现缓存未命中。应在阶段边界执行，并比较后续累计成本；不要为了提高命中率永远保留大上下文，也不要每几轮就压缩一次。

`roles.*.maxTokens` 限制的是每次响应的输出上限，不是 child 总 token 或总费用预算；把它调得很低可能增加截断与续写次数，不能替代上述预算治理。

## 对费用的直观解释

以当前 Go 文档列出的 Flash 单价举例，WP2 这份用量按其峰/谷价分别约为 $0.78 / $0.39；如果将缓存读取全部错误地按普通输入计算，会得到明显更高的结果。这只是按 **2026-11-03 查询价格** 做的算例，不能替代 11 月 2 日账单、套餐额度扣减或实际峰谷时段。[当前 Go 价格与额度口径](https://opencode.ai/v2/docs/console/go/#usage-limits)

因此，本次最先应解决的是：把实际成本看清楚、约束长循环与大回显，再补齐逐会话路由缓存；不宜仅通过更换模型或开启一个所谓的“KV 开关”处理。
