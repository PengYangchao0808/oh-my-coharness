## 0. 一页摘要

| 问题 | 本版回答 |
|---|---|
| 谁来编排多 Agent？ | **DSH 主 Agent**（原生对话 + Workflow + Subagent）；OMC 不新增编排器 |
| Council 怎么做？ | 一个 Skill：一次 `coharness({ action:'dispatch', tasks:[...] })`，两个不同 Harness 只读并行，主控合成 |
| ULW 怎么做？ | 一个 Skill：Plan → Explore → Build → Review → Verify，阶段门禁靠纪律与证据 |
| 角色怎么分工？ | 装了 slim 用 slim 的 `subagent_*`；没装则用 Skill 里的角色契约 + `coharness` 选 Harness |
| 写入怎么隔离？ | 0.2.0 默认只读；写必须显式 `in-place` + 用户同意；**不做并行写入**；隔离 Worktree 留到 0.2.1+ |
| 后端/前端怎么并行？ | 先定契约；并行只做调研/只读；写入串行；集成与验收由主控统一做 |
| 会新增工具/动作吗？ | **不会。** 工具仍是 `dispatch / list / doctor`，Schema 不变 |

**四条原则**

1. **能用 DSH 原生功能，就不写 OMC 代码。** Subagent 生命周期、子会话、完成通知、Workflow、工作目录、可视化都优先交给宿主。
2. **不建立跨 Agent 通信网络。** 外部 Agent 不直接互相发消息；DSH 主控接收结果、判断依赖、再派发下一步。
3. **前后端独立开发、独立验收。** 后端只提供标准工具与状态；前端优先复用 Desktop 已有组件，不让 GUI 阻塞工作流发布。
4. **先同步 OMO Slim 基元，再考虑新功能。** 角色、Council、ULW、后台委派、验收门禁优先；暂不做动态评分系统。

## 1. 定位：一个薄桥接层，两种入口

```text
DSH Desktop / CLI
  原生对话 · 子 Agent 面板 · 工具结果 · Workflow 可视化 · 工作区
        │
        ├── DSH Native
        │     subagents · workflowEngine · skills · worktrees（可选）
        │
        ├── OMO Slim Companion（可选）
        │     角色 · Preset · Council · 配置卡
        │
        └── Oh My CoHarness（薄桥接）
              coharness 工具 · Harness Registry · Harness 选择 · Skills
                    │
                    └── 现有 v0.1 执行层
                          dispatch.js · provider.js · transport.js
                                │
                                └── Codex / Kimi / OpenCode / GLM / AGY
```

| 模式 | 用户安装 | 编排由谁负责 | OMC 的角色 |
|---|---|---|---|
| **Standalone** | 只装 OMC | DSH 主 Agent + OMC Skills | 提供外部 Harness 通路与工作流纪律 |
| **Companion** | OMC + `oh-my-dsh-slim` | Slim 的角色体系 + OMC 外部 Harness | 只做外部 Harness 适配与协作提示 |

**Companion 的硬规则**

- **只能有一个主编排者。** Slim 的 preset 是主 Agent；OMC 不再注册 `subagent_oracle` / `subagent_fixer` 等角色工具。
- Slim 负责**内部角色**（同模型、可续接、有角色 prompt），OMC 负责**外部 Harness**（Codex / Kimi / GLM / AGY / OpenCode）。
- 主控收到结果后自己判断依赖，再决定下一次 `coharness` 或 `subagent_*`；外部 Agent 之间不建立点对点通道。
- 两边都不能假装「已经兼容」：**检测到插件 ≠ 验证了工具可见性**（见 §5 PR-3）。

## 2. 复用矩阵与边界

### 2.1 DSH 原生能力：哪些直接用，哪些条件用

| DSH 能力 | 能替代 OMC 的什么 | v0.2 决策 |
|---|---|---|
| `ctx.subagents` | 启动、生命周期、容量、取消、完成通知、子会话 | **直接复用** |
| `ctx.workflowEngine` + `workflow` 工具 | 脚本式并行、流水线、阶段记录、Workflow UI | **条件复用**：只用于 DSH 原生 / 同一 provider 的任务 |
| `ctx.agentTeams` | DSH 子 Agent 消息、任务板、协作 | **不强依赖**：实验性，且面向可续接的本地 teammate |
| `ctx.worktrees` | Git 独立工作树 | **0.2.0 不用**；0.2.1+ 再评估（见 §2.3） |
| `ctx.skills` | Skill 发现、注册、按需加载 | **直接复用** |
| `todo_write` | 任务清单与阶段进度 | **直接复用** |
| Desktop 子 Agent UI | 执行状态、子会话、结果展示 | **不重写** |
| Workflow UI | 阶段与子任务可视化 | **直接复用**（走到原生 Workflow 时） |

### 2.2 边界：原生 Workflow 不能替代混合 Harness 编排

DSH 0.2.1-rc.3 的 Workflow 已支持 `agent()`、`parallel()`、`pipeline()`、`phase()`、`log()`，脚本在受限 PTC 进程里执行。但它有一个关键约束：

- **一次 run 只有一个 `subagentProvider`**（`WorkflowStartRequest.subagentProvider`）；
- 脚本里的 `agent(prompt, { provider })` 的 `provider` 是**模型路由**，不是 subagent 路由；
- 子 Agent 的 `cwd` 固定来自 `ctx.workingDirectory.ensure(parent)`，没有 per-agent cwd；
- OMC 的 provider 声明 `outputSchema: false`，结构化返回不可用。

所以决策是：

| 任务形态 | 用什么 |
|---|---|
| 多个 **DSH 原生 Agent**（同一 provider、需要阶段/并行/UI） | **官方 `workflow` 工具** |
| 多个**同类 Provider** 子任务（全部 Codex，或全部 Kimi） | 可以评估官方 `workflow`（run 级 `subagentProvider: omc:<id>`） |
| **Codex + Kimi + GLM 混合**并行 | **`coharness({ tasks:[...] })`** |
| **有依赖的跨 Harness 工作流** | **DSH 主控按阶段分别调用 `coharness`**，每步拿 `DispatchResult` 再决定下一步 |

结论：**不自己写 Workflow Engine，也不把外部 Harness 强行包装成官方 Workflow 的 provider 路由。** 两者各做自己擅长的部分。

### 2.3 为什么不在 0.2.0 做 Worktree

- `ctx.worktrees.create(agent)` 的真实语义是：创建一个新 checkout，并通过 `ctx.workingDirectory.set` **把整个会话切过去**；它不是「给某个 child 一个隔离 cwd」。
- linked worktree 的 `.git` 文件写的是 Windows 绝对路径（本机实测 `gitdir: E:/...`），WSL 侧无法按该路径解析；CLI 自己的 `git status` / `git diff` 会失败。
- 因此 0.2.0 **不做隔离工作区**：默认只读；写必须显式 `in-place` + 用户同意；**不做并行写入**。等 0.2.1+ 有可靠的 per-child 隔离方案，再开放「并行写入」。

这不是放弃隔离，而是把「未验证的隔离」排除在发布门槛之外。

## 3. 先同步哪些 OMO Slim 基元

不复制整套 OMO Slim，也不同名注册它的角色工具。只同步真正影响体验的基元：

| OMO Slim 基元 | OMC 0.2.0 的最薄实现 | 优先级 |
|---|---|---|
| Orchestrator | DSH 主 Agent 本身 | P0 |
| Explorer / Oracle / Fixer / Designer / Librarian | 装了 slim 用其 `subagent_*`；Standalone 用 Skill 里的角色契约 + `coharness` 选 Harness | P0 |
| Council | **一个 Skill + 现有 `tasks[]`**，不新增 action | P0 |
| Background Delegation | 现有 `delivery:'background'` + 宿主完成通知 | P0 |
| Deepwork / ULW | **一个 Skill**：阶段与验收门禁 | P1 |
| Verification Planning | **一个 Skill** + DSH 现有测试工具 | P1 |
| Preset Switching | Companion 用 Slim 配置卡；Standalone 用现有 YAML | P1 |
| Worktree | DSH 实验性能力，0.2.0 不用 | P2 |
| Companion / 专属 UI | 优先 DSH 原生任务界面；不写客户端 | 暂缓 |

### 3.1 与 oh-my-dsh-slim 的协作方式

oh-my-dsh-slim v0.8.5 已有 orchestrator + 五个角色、Council 三席 + synthesizer、角色模型继承和设置卡。OMC **不再注册**：

```text
subagent_oracle / subagent_designer / subagent_fixer /
subagent_explorer / subagent_librarian / subagent_council
```

而是：

```text
oh-my-dsh-slim Orchestrator（主 Agent）
  ├─ Internal Specialists  → 原生 subagent_*（slim 提供）
  └─ External Specialists  → coharness（OMC 提供）
        ↓
     主控接收结果并决策；双方不建立另一套消息协议
```

OMC 只给主控一份很短的补充说明（写进 `coharness` Skill）：

> 当任务明显受益于外部原生编程工具时，使用 `coharness`；其他角色任务继续使用原来的 `subagent_*`。不要重复启动同一任务，也不要让外部执行者管理 DSH 内部团队。

**Companion 的实现方式**：一个可选的 Skill 段落 + doctor 检测，不修改 Slim 源码。若需要 Slim 侧提供「外部 Harness 委派」扩展点，优先向上游提交可选的 PR，而不是长期维护私有 Fork。

### 3.2 必须核验、不能假设的事

- Slim 的现有 Preset 是否确实向主 Agent 暴露 `coharness`；
- 原有的工具过滤规则是否会阻止调用；
- `subagent_*` 是否真的可见、是否与 OMC 的 provider 名称冲突。

**检测到插件不等于验证了兼容。** doctor 只能说 `detected` / `unverified`；真正的兼容性由验收 Case B 证明。

### PR-1 — 同步 OMO Slim 基元（alpha.1）

**目标**：先让「Council / ULW / Verify」以 Skill 形式可用，**不改 dispatch**。

**文件**

- `src/skills.js`：注册表增加三项，并 `export const SKILLS` 供自检复用。
- `scripts/check.mjs`：从 `SKILLS` 读取目录列表，不再硬编码 2 个 Skill；输出动态数量。
- `skills/coharness-council/SKILL.md`
- `skills/coharness-ulw/SKILL.md`
- `skills/coharness-verify/SKILL.md`
- `skills/coharness/SKILL.md`：加三行指针（什么时候加载哪个）。
- 可选：`src/index.js` 的 `DESCRIPTION` 加一句「独立评审用一次 `tasks[]` 派两个只读任务；多阶段工作加载 `coharness-ulw`」。

**`coharness-council` 的规则**

- 触发：用户明确说「council / 共识 / 多模型看看 / 独立意见 / 不要只用一个模型」。
- 先 `coharness({ action:'list' })`；选 **两个不同** Harness；不足两个 → 单派发并说明，不假装 council。
- 一次调用、只读、同步：

```js
coharness({
  action: 'dispatch',
  mode: 'read-only',
  delivery: 'await',
  tasks: [
    { harness: 'codex', prompt: 'Independently review this design. Report concrete risks and evidence.' },
    { harness: 'glm',   prompt: 'Independently review this design. Report concrete risks and evidence.' }
  ]
})
```

- 每个席位只看到问题，不看到其他席位答案；任务文本里写清「独立回答」。
- 主控综合：共识 / 分歧 / 未验证 / 建议 / 置信度；每条结论标 `seat A (codex)` 这类来源。
- 一席失败 → 只用完成的一席，并明确说「这次不是完整 council」；0 席完成 → 如实失败。
- 成本：默认 2 席；不要为普通问题触发。

> PR-1 阶段只演示「两席都成功」的路径；一席失败 / 无效 harness 的降级依赖 PR-2 的 per-task 隔离。alpha.1 的发布说明要写清这一点。

**`coharness-ulw` 的规则**

- 触发：用户要「做完整 / 实现并审查 / 修到测试过 / 多阶段」。
- 阶段：**Plan → Explore → Build → Review → Verify**；用 `todo_write` 把阶段写出来。
- 门禁：
  - Build 没完成，不开始 Review；
  - Review 没给出 `approve`，不进入 Verify；
  - Verify 没有真实退出码，不说「完成」；
  - 最多一轮修复 + 复核；不无限循环。
- 输出契约：Build 最后一行 `STATUS: done | partial | blocked`；Review 最后一行 `VERDICT: approve | request-changes | insufficient-context`；没有 footer 就按「未完成 / 上下文不足」处理，不猜通过。
- 写入：**单写者**；必须显式 `mode:'in-place'`，并先告诉用户「这会用该 CLI 自己的权限写文件」；**不做并行写入**。写路径可能是 direct（`surface:'direct'`，没有子会话/容量），报告里要说明。
- 调研：可以并行 `tasks[]` 只读；默认 2–3 个。
- 交接：每步给下一段最小上下文（目标、改的文件、结论、证据、未决问题），不贴整段对话。
- Companion：如果 `subagent_*` 可用，内部角色用 slim，外部 CLI 用 `coharness`；同一任务不两边重复跑。

**`coharness-verify` 的规则**

- 按风险定证据：
  - 低（文档/只读/小改）：类型检查或单测；
  - 中（逻辑/API）：单测 + 集成测试；
  - 高（认证/数据/迁移/UI）：集成 + 手动/视觉 + 回滚方案。
- 证据必须包含：命令、退出码、输出尾部；没有退出码就是「未验证」。
- 用 DSH 现有测试工具；不新增 OMC 执行器。
- 测试不存在 → 提出最小测试建议，不假装通过。

**测试**

- `skills.js` 注册 5 个 Skill；`check.mjs` 从 `SKILLS` 读取并输出动态数量；frontmatter 可解析；旧 17 个用例不变。
- 不需要真实 CLI 的 skill 文本快照（可选）。

**演示**：`coharness({action:'dispatch', tasks:[codex, glm]})` 两席并行，主控输出共识/分歧；alpha.1 发布。

### PR-2 — Dispatch 可靠性修补（beta.1）

**目标**：不新增执行器，只修 v0.1 五个真实问题。

| # | 当前行为 | 0.2.0 修补 |
|---|---|---|
| 1 | auto 选第一个 `auth !== 'missing'`，可能选到 `signed-out` | 优先 `auth === 'ok'`，再用定义表的 `verified` 排序（**argv 实测标记，不是运行时成功率**）；排除 `signed-out`；显式点名 signed-out 允许但警告 |
| 2 | `tasks[]` 超过 `maxParallel` 时静默 `omitted` | 抛 `OMC/TOO-MANY-TASKS`，给出 `maxParallel` 和「拆成多次」建议；不丢任务 |
| 3 | 某个 `resolveTarget` 抛错会让整批 `Promise.all` 拒绝 | 每个 task 独立 try/catch，返回该 task 的失败结果，其他任务照常完成 |
| 4 | provider 与 direct 接受的参数不同，降级时无说明 | `DispatchResult` 增加可选 `surface`（`provider` 或 `direct`）与 `downgradeReason`；文本输出明说 |
| 5 | `delivery:'background'` 在 direct 路径上被静默 await | 直接返回 `OMC/BACKGROUND-UNSUPPORTED`，建议 `await` 或改只读默认模式 |

**Skill 增补**：`surface:'direct'` 时报告要说明「没有 childId / 容量」；`TOO-MANY-TASKS` 时拆成多次调用；`BACKGROUND-UNSUPPORTED` 时改 `await`。这三句写进 `coharness` Skill 的失败/报告段，避免模型把降级当成完整能力。

**只读能力的声明**

- 现有输出已经说明 `mode` 只对带沙箱开关的 CLI 生效；0.2.0 把话说全：
  - 强制沙箱：`codex -s read-only`、`gemini --approval-mode plan --skip-trust`、`antigravity --sandbox`；
  - 仅 advisory：`opencode`、`kimi`、`glm`。
- Skill 要求：评审优先用强制沙箱的三个；用 advisory 的 CLI 做「只读」时，主控要提醒用户它可能仍会写。

**测试**

- auto：`ok` 优先于 `unknown`；`signed-out` 不参与 auto；无可用时给出逐行原因。
- over-limit：5 个 task + `maxParallel=4` → `OMC/TOO-MANY-TASKS`，不返回 `omitted`。
- 部分失败：一个 task 的 harness 不存在，另一个仍 `completed`。
- surface：写模式（非默认）走 direct，结果带 `surface:'direct'` 与原因。
- background：direct + background → `OMC/BACKGROUND-UNSUPPORTED`。
- 真实回归：两个只读任务并行，总耗时 ≈ max。

**文件**：`src/dispatch.js`、`src/index.js`（渲染/描述）、`skills/coharness/SKILL.md`（失败表新增 `TOO-MANY-TASKS` / `BACKGROUND-UNSUPPORTED`）、`test/smoke.test.mjs`。不新增模块。

## 6. 关键实现细节

### 6.1 Council 的「一次调用」语义

- `tasks[]` 是 v0.1 已有的并行原语；两席就是两个 task。
- `delivery:'await'` 让工具等所有席位结算；`Promise.all` 在 PR-2 之后按 task 隔离失败。
- 两个席位必须是**不同 Harness**；同 Harness 跑两次是重复采样，不是 council。
- 主控不把两席输出直接拼接；必须做共识/分歧/证据的合成。
- 不做「多数票」；两席冲突时看证据，而不是看谁票多。

### 6.2 `surface` 与降级原因

PR-2 之后，每个 `DispatchResult` 带：

```text
{
  "status": "completed",
  "harnessId": "codex",
  "surface": "provider | direct",
  "downgradeReason": "mode in-place differs from provider default read-only; direct run has no child session/capacity"
  // ...
}
```

文本输出示例：

```text
#1 codex · completed · 3.2s · surface: provider · child sess-...
#2 codex · completed · 2.8s · surface: direct · mode in-place has no provider child
```

这样模型和用户都知道：direct 路径没有 `childId`、没有宿主容量、没有子会话面板；取消仍由 `exec.signal` 与进程树负责。

### 6.3 Companion 检测

- `ctx.tools.get()` 是唯一可靠的能力探测；不要读 Slim 的源码或配置文件。
- 角色工具可能是 agent-scoped：host 侧无 scope 的 `ctx.tools.get()` 可能看不到。检测不到时输出 `not detected (may be scoped)`，不要断言「Slim 未安装」。
- 只报告「检测到哪些角色工具」；不报告「已兼容」。
- `coharness` 自身是否可见，用 `ctx.tools.get('coharness')` 判断；但 Slim preset 的工具过滤是否放行，doctor 看不到 → `unverified`。
- 真正的兼容性必须在 Case B 里跑一次：Slim 主控能调用 `coharness`，外部 CLI 返回结果，内部角色仍可用。

### 6.4 ULW 的交接包

每次阶段交接只传最小集合：

```text
GOAL: 一句话目标
CONTRACT: 接口 / 数据格式 / 文件归属 / 验收命令
DONE: 已完成的改动与命令
EVIDENCE: 测试退出码 / diff / 关键输出
OPEN: 未决问题与风险
NEXT: 下一阶段要做什么
```

不传整段对话；不传密钥；不传无关文件。

### 6.5 通信拓扑

```text
DSH Lead（唯一调度与交接中心）
  ├─ DSH 原生 Agent：原生消息 / subagent_*
  ├─ OMC 外部 Harness：coharness → DispatchResult
  └─ Verifier：测试证据（DSH 工具）

外部 Harness 之间：没有点对点通道。
```

所有结果回到 Lead，由 Lead 判断依赖、决定下一步；外部 CLI 只执行一次，不管理 DSH 内部团队。

**关于并发的一条注记**

`dispatch.maxParallel` 是**单次调用**里的任务数量上限，不等于跨多次调用的全局并发控制：

- provider 路径受宿主 `maxActiveSubagents`（默认 8）约束；
- direct 路径没有宿主容量槽，必须单独测试并发与写入风险；
- 0.2.0 的 ULW 不做并行写入：direct 路径最多承载一个串行写任务，其余是只读任务；并发与写入风险要分别测试。

## 附录 A：宿主事实（决定边界）

核查对象：本机 `DeepSeek Harness/resources/app.asar`（`@deepseek-ai/dsh-desktop-runtime@0.2.1-rc.3`）与运行中的 Host Service 目录。

| 事实 | 读数 | 对 0.2.0 的影响 |
|---|---|---|
| 原生 Workflow | 存在；`agent/parallel/pipeline/phase/log`；`WorkflowStartRequest.subagentProvider` 是 run 级路由 | DSH 原生/同 provider 用它；混合 Harness 用 `coharness` |
| `agent()` 选项 | `label / phase / schema / provider / model`；`provider` 是模型路由 | 不能在一个 run 里按脚本切 Harness |
| 子 Agent cwd | `ctx.workingDirectory.ensure(parent)` | 没有 per-agent cwd；跨目录写入要主控分步 |
| `ctx.worktrees.create` | 创建并**进入**新 checkout（`workingDirectory.set`） | 不是 per-child 隔离；0.2.0 不用 |
| linked worktree | `.git` 内容为 `gitdir: E:/...`（Windows 绝对路径） | WSL 侧 git 不可读；不采用 |
| 外部子会话 | one-shot；`caller` 不写父 catalog；`maxActiveSubagents` 默认 8 | 外部 CLI 不能续接；trace 用 `childId` |
| 工具调用超时 | 只对声明了上限的工具生效；`coharness` 无上限 | 长调用会占住一轮；只读用 background |
| `agentTeams` | 面向可续接本地 teammate | 外部 CLI one-shot，不用 |

> linked worktree 的结论来自 `.git` 文件内容 + 路径语义（本机实测文件内容为 `gitdir: E:/...`）；受 DSH 受限 shell 的 `Wsl/E_ACCESS_DENIED` 限制，没有在 WSL 内直接跑 `git status`。0.2.0 直接不用它，避免把推断当验证。
